HyperLaw — Final Production Update (Master Implementation Specification, Revised)

Objective

Treat this document as the primary implementation specification for HyperLaw.

Before building any new features, compare this specification against the current codebase and produce an implementation report identifying:

* ✅ Completed
* 🟡 Partially Implemented
* ❌ Missing
* ⚠️ Needs Revision

Do not remove existing functionality unless it conflicts with this specification.

The goal is to prepare HyperLaw for production while maintaining a clean, intuitive, trustworthy user experience.

⸻

Core Product Philosophy

HyperLaw is an AI-powered legal self-help platform that helps users:

* Organize legal information
* Upload and manage case files
* Draft legal documents from user-provided facts
* Learn general legal concepts
* Track deadlines
* Prepare for legal matters
* Stay organized throughout their case

HyperLaw is not a law firm.

HyperLaw does not provide legal representation.

HyperLaw does not create an attorney-client relationship.

HyperLaw does not make legal decisions for users.

**HyperLaw does not create any relationship of trust or reliance between the user and HyperLaw regarding the accuracy or applicability of any output.** The user remains responsible for every legal decision and every document submitted.

**Data retention setting must be explicitly decided before launch, not deferred.** Confirm whether the Anthropic API account has Zero Data Retention (ZDR) enabled. This is not a "future option" — a February 2026 federal ruling (*United States v. Heppner*, S.D.N.Y.) found that documents generated through standard-retention Claude access were not protected by attorney-client privilege, specifically because the platform's data policy "fatally compromised" confidentiality. Since HyperLaw processes uploaded complaints and case-specific facts, this decision affects real user data now, at launch, not at some later maturity stage.

AI Architecture

Create two AI layers.

Layer One

Internal HyperLaw Knowledge Library.

Contains:

* Legal glossary
* Court terminology
* Procedural explanations
* Definitions
* General educational material

No AI request should occur when information already exists locally.

Store this information in a centralized database or structured content system so it can be updated without changing application code.

**Layer One is not exempt from disclaimer requirements.** Court precedent (a Tennessee bankruptcy court; the North Carolina State Bar) has found that even defining legal terms or explaining procedural concepts can itself constitute legal advice under some states' unauthorized-practice-of-law rules. Every Layer One response — glossary lookups, term definitions, procedural explanations — must display the same compliance notice treatment as Layer Two (personalized/AI-drafted) output, pulled from the same centralized Compliance Language Manager described below. Do not treat Layer One as a "safe, no-disclaimer-needed" tier.

⸻

Layer Two

Claude API.

Only use Claude when personalization or drafting is required.

Examples:

* Complaint drafting
* Motions
* Demand letters
* Affidavits
* Declarations
* Tutor conversations about the user's own case
* Case organization

Always minimize unnecessary API usage.

⸻

AI Behavior

Review every prompt and response template.

The AI should consistently:

* Explain concepts.
* Organize user information.
* Draft documents from user-provided facts.
* Encourage review before filing.
* Encourage verification of court rules.

Avoid wording that implies HyperLaw is making legal decisions or guarantees. The AI should present information in a neutral, educational way and avoid directing users toward a particular legal strategy or predicting legal outcomes. Specifically, the AI should never say or imply: "you should file," "I recommend," "you will win," "this is a strong case," or similar outcome-predictive or strategy-directive language, in either Layer One or Layer Two output.

⸻

Compliance Language System

Create a centralized Compliance Language Manager.

Do not hardcode legal notices throughout the application.

Store centrally:

* AI disclaimer
* Review before filing notice
* Educational disclaimer
* Jurisdiction reminder
* No attorney-client relationship notice
* **No relationship of trust or reliance notice** (distinct from the attorney-client notice — states this explicitly regarding reliance on HyperLaw's output generally)
* Legal self-help notice
* Payment disclosure
* Privacy notices
* Terms acknowledgment
* Export notices
* Data retention / confidentiality notice (see Privacy & Data section below)

Every screen should reference these centralized resources, including Layer One glossary/informational screens.

Changing one notice should update it everywhere.

⸻

Jurisdiction Awareness

Whenever drafting begins:

Ask:

"What state or jurisdiction does this matter involve?"

Store this value with the case.

Display a reminder that laws and court procedures vary by jurisdiction.

**Design this so the jurisdiction value can eventually drive which compliance notice variant is shown** (e.g., a more detailed disclaimer for jurisdictions with broader unauthorized-practice-of-law definitions). This does not need to be fully built in v1, but the jurisdiction field and Compliance Language Manager should be architected so state-specific notice variants can be added later without a rebuild.

Verification Workflow

Before any document can be exported:

Require completion of a verification flow.

Checklist includes:

☐ I reviewed all facts.

☐ I reviewed dates.

☐ I reviewed names.

☐ I reviewed formatting.

☐ I reviewed citations.

☐ I reviewed deadlines.

☐ I understand I am responsible for everything filed with a court.

Only then allow export.

⸻

Pre-Verification Reader

Implement a Pre-Verification feature.

Users can select any generated document.

The application reads the document aloud while highlighting each word with an orange glow.

Purpose:

Help users catch:

* Typos
* Missing information
* Formatting errors
* AI mistakes

Display reminders encouraging users to review the document independently before filing.

Save completed verification sessions to the case history.

Success Criteria

HyperLaw Version 1 is considered production-ready when a user can:

1. Create an account.
2. Sign in.
3. Create a case.
4. Upload a complaint.
5. Have Claude analyze the uploaded information.
6. Organize all case materials automatically.
7. Generate an AI-assisted document.
8. Complete the Pre-Verification workflow.
9. Purchase the document or use available credits.
10. Download the document.
11. Return later and manage the case from a clean, organized dashboard.

Every feature should reinforce HyperLaw's mission:

Prepare Smarter. Stay Organized. Navigate with Confidence.

Compliance Addendum (Reference — Not for Replit to Implement as Code)

The following items are tracked for the founder's own follow-up and are not application features, but are recorded here for continuity:

* **Arbitration clause in the Terms of Service** is currently a placeholder and requires review by a licensed attorney before publication — enforceability and required disclosures vary by state.
* **Entity structure**: HyperLaw currently operates under a single LLC shared with other ventures. This is a deliberate decision given solo operation and no current need to wall off other assets — documented here for the record, not an open item unless business circumstances change.
* **Refund reserve**: given precedent for treble-damages exposure in comparable unauthorized-practice-of-law litigation (Missouri), early revenue should remain in HyperLaw's own account rather than being reallocated elsewhere until a reserve buffer is established.
* **Full legal review before public launch or before accepting payment from users other than the founder** — this specification reflects legal research conducted collaboratively, not formal legal advice, and has not been reviewed by a licensed attorney.
